# 面向用户的交付回执

此文件定义 `converge` 的最终回复。它只决定如何表达已记录的事实，**不会触发新的检查、Agent、状态写入或修复轮次**。完整证据仍保存在 ledger、PDLC 产物和命令输出中。

终态先使用 `python3 "$CONVERGE_SKILL_DIR/scripts/delivery_report.py"` 以严格完成门禁验证 Schema v10；旧 Schema、Evidence v1、`controller_attested` 验收或未绑定清场不能渲染为 ready。报告只把 fresh/pass 且具有 observed Evidence Receipt v2 的 acceptance 计入“已验证”；普通 pass check 仍显示为控制器记录，但不混入验证范围。新状态以 `handoff.open_issues: []` 保存逐项问题；报告分别展示“未通过验收数”和“其他待处理数”。Git 工作区不可读时最多输出 `attention`。

## 先选用户状态

按以下优先级只选择一个状态：

| 状态 | 使用条件 | 标题 |
|---|---|---|
| `blocked` | 环境、权限、依赖或客观检查使工作不能继续 | 暂时无法继续 |
| `decision` | 存在需要用户选择的业务、范围、兼容性或发布问题 | 需你确认 |
| `attention` | 工作完成但有不阻塞使用的明确风险或后续建议 | 已完成，需关注 |
| `ready` | 所有验收项都有新鲜通过证据，且没有待确认项 | 已完成，可使用 |

`decision` 优先于 `ready`。因此不得同时写“已完成”与“需要业务确认”。`unknown`、`stale` 或未覆盖的验证不能支撑 `ready`。

## 默认回执

默认使用 `summary`，但长度和信息密度由用户状态决定：

| 状态 | 默认长度 | 必须回答 |
|---|---:|---|
| `ready` | 100–170 字 | 做了什么、是否可使用、已验证范围、交付轮与修复数 |
| `attention` | 120–180 字 | 当前行为、已验证范围、需关注的影响 |
| `decision` | 160–260 字 | 当前行为、已验证和未验证范围、需要选择什么、推荐方案 |
| `blocked` | 120–180 字 | 已完成到哪里、为何不能继续、需要提供什么 |

没有信息就不输出栏目。首行必须是“状态 + 对用户有意义的结论”。`ready` 可使用三行简报；其他状态使用下面的四层结构：

```text
结果：<状态标题>：<一句结论>
关键改动：<最多五项面向用户的变化；没有则省略>
当前情况：<用户现在实际可使用的行为，或已完成到的边界>
已验证范围：<仅从 fresh/pass 且 observed 的 acceptance/检查派生的业务场景>
证据等级：<observed；另有多少 controller records 未计入验证>
说明（controller_attested）：<handoff.last_verification；仅作控制器说明，不是 verified 证据>
过程：<交付轮数；修复的确认问题数；待处理项数>
未验证/影响：<未覆盖范围及其实际影响（如有）>
下一步：<无需行动 | 一个明确的推荐选择>
```

- `converge`：使用“完成”说明行为变化；只在存在待决项时显示“下一步”。
- “已验证范围”只能由结构化 `ledger.acceptance` 的 fresh/pass observed Evidence Receipt v2，以及未来同等级的结构化 check receipt 派生；当前无 receipt 的 pass check 明示为控制器记录且不计入。不得把 `handoff.last_verification` 自由文本渲染为“已验证”。
- 独立只读检查由 `converge-review` 按自己的结果格式输出，不复用交付完成文案。
- 同一任务再次检查时只报告相对上一份回执的变化：新增发现、已解决项、状态变化；没有变化时使用短回执明确“无新增变化”。`delivery_report.py` 返回 `next_report_history`，控制器必须用独立 revision 写入 ledger；不得与阶段推进、验收变更或计划确认混写。
- JSON 回执的 `execution_metrics` 只汇总已签名 runner 回执中明确给出的 `usage.total_tokens`；当前宿主未提供签名用量时，token、工具调用和用户阻塞均标为“不可用”。不得由提示词长度、日志行数、等待次数或模型估算补造指标。

## 需要用户决定时

一次只呈现优先级最高的一项，并给出推荐和原因。`decision` 回执必须先交代当前实现能做什么、未决定事项影响什么，不能只抛出一个抽象问题：

```text
需要你确认：<业务问题>
推荐：<推荐选择>。
原因：<不超过一句的实际影响>。
可选：<选项 A>；<选项 B>。
```

其他低优先级建议写为“另有 N 项建议，可按需查看”，不要挤占默认回执。

## 验收矩阵与技术详情

在 `attention` 或 `decision` 状态下，存在三个及以上可比较的业务场景时，追加业务验收表：

| 场景 | 结果 | 说明 |
|---|---|---|
| <业务场景> | 通过 / 需确认 / 未验证 | <面向业务的说明> |

用户明确要求“详细报告”“技术细节”“测试命令”“为什么”时，才追加技术证明包：测试名称和结果、命令和退出码、文件/接口、基线、引擎、状态阶段、lease 与问题证据。普通默认回执可以写“1 个交付轮”，但不得出现 `complete`、`blocked_decision`、`P0/P1/P2`、`fresh`、`lease`、`稳定轮` 等内部术语。

## 最终自检

发送前逐项检查：

1. 第一行能否让负责人知道是否需要行动？
2. 是否把待确认事项错误地说成“已完成”？
3. 每个“通过”是否有本轮真实证据，并说明了验证范围？
4. `attention`/`decision` 是否说明了当前行为、未验证范围和实际影响？
5. 是否删除了无变化、空栏目、重复命令和 Agent 内部术语？
6. 下一步是否只有一个清晰、可执行的选择？
7. 是否用一行说明了交付轮数、已修问题数和待处理项？

任一项不满足，重写回执；不得重新跑检查来凑报告内容。
