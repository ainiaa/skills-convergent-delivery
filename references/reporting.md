# 面向用户的交付回执

此文件定义 `converge` 的最终回复。它只决定如何表达已记录的事实，**不会触发新的检查、Agent、状态写入或修复轮次**。完整证据仍保存在 ledger、PDLC 产物和命令输出中。

## 先选用户状态

按以下优先级只选择一个状态：

| 状态 | 使用条件 | 标题 |
|---|---|---|
| `blocked` | 环境、权限、依赖或客观检查使工作不能继续 | 暂时无法继续 |
| `decision` | 存在需要用户选择的业务、范围、兼容性或发布问题 | 需你确认 |
| `attention` | 工作完成但有不阻塞使用的明确风险或后续建议 | 已完成，需关注 |
| `ready` | 所有验收项都有新鲜通过证据，且没有待确认项 | 已完成，可使用 |

`decision` 优先于 `ready`。因此不得同时写“已完成”与“需要业务确认”。`unknown`、`stale` 或未覆盖的验证不能支撑 `ready`。

## 默认回执

默认使用 `summary`，目标 80–160 个汉字；没有信息就不输出栏目。首行必须是“状态 + 对用户有意义的结论”，随后最多三项：

```text
结果：<状态标题>：<一句结论>
完成/发现：<最重要的行为变化或发现>
验证：<已验证的业务场景；未验证的范围（如有）>
下一步：<无需行动 | 一个明确的推荐选择>
```

- `execute`：使用“完成”说明行为变化；只在存在待决项时显示“下一步”。
- `review`：使用“发现”，不称“交付完成”；无实质问题时直接说明“在本次检查范围内未发现问题”。
- `plan`：使用“推荐方案、影响、需要确认”，不假装已经验证或实现。
- 同一任务再次检查时只报告相对上一份回执的变化：新增发现、已解决项、状态变化；没有变化时一句说明即可。ledger 中记录已报告的问题指纹和待决项，避免重复叙述。

## 需要用户决定时

一次只呈现优先级最高的一项，并给出推荐和原因：

```text
需要你确认：<业务问题>
推荐：<推荐选择>。
原因：<不超过一句的实际影响>。
可选：<选项 A>；<选项 B>。
```

其他低优先级建议写为“另有 N 项建议，可按需查看”，不要挤占默认回执。

## 验收矩阵与技术详情

仅在存在三个及以上可比较的业务场景时，追加业务验收表：

| 场景 | 结果 | 说明 |
|---|---|---|
| <业务场景> | 通过 / 需确认 / 未验证 | <面向业务的说明> |

用户明确要求“详细报告”“技术细节”“测试命令”“为什么”时，才追加技术证明包：测试名称和结果、命令和退出码、文件/接口、基线、引擎、轮次、lease 与问题证据。普通默认回执不得出现这些内部字段，也不得用 `complete`、`blocked_decision`、`P0/P1/P2`、`fresh`、`lease`、`稳定轮` 等术语。

## 最终自检

发送前逐项检查：

1. 第一行能否让负责人知道是否需要行动？
2. 是否把待确认事项错误地说成“已完成”？
3. 每个“通过”是否有本轮真实证据，并说明了验证范围？
4. 是否删除了无变化、空栏目、重复命令和 Agent 内部术语？
5. 下一步是否只有一个清晰、可执行的选择？

任一项不满足，重写回执；不得重新跑检查来凑报告内容。
